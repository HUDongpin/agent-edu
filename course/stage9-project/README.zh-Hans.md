# 第 9 阶段 —— 迁移项目

咖啡馆是共用的练习。这一阶段要求你，在一个你真正懂的领域里，把控制边界说清楚。

## 第一个小时

先做三步，然后停下来看。这一阶段剩下的工作，是拿这三步显出来的东西继续做。

1. 选一个你真正做过的领域。用一句话说清谁站在那里，以及他们要完成什么。
2. 写三句会打破关键词规则的输入。如果一份短词表会把它们判错，你就碰到了那堵墙。
3. 按 [`eval-template.json`](eval-template.json) 的形状写五个评测用例：一个普通的，一个处在边界上的，一个带敌意的，另外两个取自上面的输入。

在仓库根目录检查这个文件。第一条命令检查本目录里的模板，第二条把同一个文件当参数传进去：

```bash
npx tsx course/stage9-project/validate.ts
npx tsx course/stage9-project/validate.ts course/stage9-project/eval-template.json
```

这两条都会接受那三个占位用例，并打印一条说明。换成你自己的文件时，至少要有五个用例。这里没有模型调用。通过这次检查并不是项目的分数。[`RUBRIC.md`](RUBRIC.md) 仍然是给这份作品打分的方式。

交付物是一份可被检查的论证，下面垫着一小件能跑的作品：

1. 把 [`artifact-template.md`](artifact-template.md) 复制进你的项目笔记。
2. 复制 [`eval-template.json`](eval-template.json)，用你自己领域里的输入替换占位用例。
3. 做出最小的规则版，以及最小的模型辅助版，让这些用例能暴露出有意义的差别。
4. 在最不可逆的动作前面放上一道可强制执行的闸门。
5. 用 [`RUBRIC.md`](RUBRIC.md) 做自评，或请同伴/老师审阅。

[`worked-example.md`](worked-example.md) 是一个做完的项目 —— 图书馆的还书台 —— 填进同一份模板，并按同一份量规打分。直到第 8 阶段，课程一直把做好的例子递到你手里，而第 8 阶段是它停下来的地方；在那个时刻才第一次看见成品长什么样，是一件奇怪的事。它是一个站得住的答案，而不是那个答案，而且故意不完美：它得了 12 分中的 11 分，丢掉的那一行被标出来并解释过，而不是悄悄修好。

**卡住了？** 提示 1 和提示 2 在 [HINTS.zh-Hans.md](../HINTS.zh-Hans.md)，然后看 [SOLUTIONS.md](../SOLUTIONS.md)。提示覆盖的是引导阶段（0–8）。这一阶段是迁移项目。

不要在提交里放入真实的 API 密钥、Authorization 头、未经处理的服务商错误正文、个人数据，或未脱敏的学习者/顾客记录。一份本地控制台记录、脱敏后的用例轨迹，或一小段 JSON 结果，就足够作为证据。

量规故意不为选择某一个框架、某一家服务商或某一条提示词加分。它为可观察的边界、成比例的控制和关于失败的诚实证据加分。

本阶段的模板（`artifact-template.md`、`eval-template.json`、`RUBRIC.md`）和完整范例（`worked-example.md`）目前仍是英文，没有翻译。代码注释和 `TODO` 标记也保持英文。把它们填成你自己领域里的论证即可。
