# 第 7 阶段 —— 保证检查会发生

**目标：** 别再指望模型自己审阅自己的工作，让审阅在结构上无法被跳过。

```bash
npx tsx course/stage7-graph/run.ts
```

两个 `TODO`：路由器，以及审阅节点。然后：

```bash
npx tsx course/check.ts 7
```

**卡住了？** 提示 1 和提示 2 在 [HINTS.zh-Hans.md](../HINTS.zh-Hans.md#第-7-阶段)，然后看 [SOLUTIONS.md](../SOLUTIONS.md)。

## 要注意什么

`run.ts` 会把同一封投诉送两遍 —— 一遍接上审阅节点，一遍绕过它 —— 然后打印本来会发给顾客的内容。

审阅关掉时，一份不合政策的回复会到达一个真人。打开时，草稿会被退回来重写，第二次尝试才发出去。

这两次运行之间，模型本身没有任何变化。变的是：**图上没有任何一条到达「发送」的路径，可以不经过「审阅」。**

## 循环 vs 图，落到具体处

在第 5 阶段，你可以往提示词里加 *"always check your reply against the refund policy"*。它有时会做。那是一条请求。

在这里，`send()` 只从一处被调用，而那一处在 `review()` 的下游。那是一条保证。差别不在模型勤不勤快 —— 而在于错的事情是否 *可能*。

注意这就是普通 TypeScript：函数、一个 `if`，以及带重写上限的循环。「图」不是你要安装的框架。它是你的控制流，被故意写下来，模型只在单个盒子里负责思考。

## 你放弃了什么

这张地图只处理你想到过的情况。一条既不是订单、也不是问题、也不是投诉的消息，会掉出路由器，打到默认分支。看默认分支怎么表现，并决定你喜不喜欢 —— 因为在生产里，意外就住在那条分支上。

## 逐条讲解 TODO

`run.ts` 里有两个 `TODO`。图本身（`handle`）已经写好了：你补的是两个模型节点。

**TODO 1：路由器。** 实现 `route`：让模型用 `ROUTE_SCHEMA` 给 `message` 分类，返回车道（`order` / `question` / `complaint`）。一次调用，低工作量 —— 这是一个便宜的决定。不要在这里写回复。

**TODO 2：审阅者。** 实现 `review`：让模型用 `REVIEW_SCHEMA` 判断 `draft` 是否符合 `POLICY`，返回 `[approved, problem]`。要严格，只按写下来的政策来判。审阅者会犯错；结构上的保证是 `send()` 只有一个调用者，并且审阅路径坐在它前面。起草者不能决定跳过那个节点。

检查器会把同一封 `COMPLAINT` 跑两遍（审阅开、审阅关），并要求一次消息只通过 `send()` 发出恰好一封回复。正确的答案看起来像：分类和审阅都走结构化输出；被拒绝的草稿带着问题说明回到起草函数。生产流程在重写次数用尽之后应当升级，而不是把一份反复被拒的草稿悄悄发出去。
