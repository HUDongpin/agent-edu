## 要注意什么

`run.ts` 会把同一份工作跑五次：一次全部打开，然后分别关掉四个部分各跑一次。每一次运行里，模型、提示词和工具都 **完全相同**。变的只是围在它们外面的代码。

| 关掉的部分 | 第二天早上会看见什么 |
|---|---|
| retry | 错误离开了运行框架；能不能恢复，现在取决于模型愿不愿意重试 |
| useful errors | 模型看见 `Error`，猜错，然后把同一个错误再试一遍 |
| permission gate | 它花了真金白银，谁都没问过 |
| run log | 出了问题，你却说不清是什么 |

当有人说「模型失败了」的时候，失败的常常是这个文件。

## 最要紧的那一个

**权限闸门。** 其余的会让你过一个糟糕的晚上；这一个花掉的钱拿不回来。

注意它住在哪里：住在 *执行* 工具的代码里，而不是提示词里。「未经询问不要下超过 £100 的单」写在系统提示词里，是一条请求。同一条规则写成工具运行器里的一个 `if`，是一条保证。模型可以被说动去违背一条请求。它说不动一个 `if`。

## 便宜、无聊，胜过聪明

这里没有一段有趣的代码。一次重试是四行。一次超时是一个参数。这就是重点：可靠性来自没人会拿去演示的、不起眼的管道，而这正是它最先被跳过、也最先被想念的原因。

## 逐条讲解 TODO

`run.ts` 里有四个 `TODO`。

**TODO 1：累计审批闸门。** 在 `callTool` 开头、任何工具真正跑起来之前：如果 `parts.gate` 开着，而且这是一次会把本轮已承诺花费推过 `APPROVAL_THRESHOLD` 的 `place_order`，就不要运行它。调用 `approve(question)`；若返回 false，就用一段人话拒绝作为错误结果返回，好让模型调整。在估算之前，拒绝未知单价，以及非正、非有限的数量。缺失的费用数据必须失败关闭，绝不能变成 $0。

阈值看的是 **合计**，不是这一笔。按单笔封顶会被绕过去：拒绝一笔 $180 的订单，模型会去下三笔 $60 的，因为它仍在试图把活干完。已经承诺的花费可以从 `tools.ORDERS` 读出来。检查器要求闸门开着时的花费不超过阈值。

**TODO 2：运行被请求的工具。** 在 `try` 里按名字从 `tools.RUNNERS` 取出函数、传入这次的参数，并返回它的结果。真实的运行框架还会给它加上超时；这里的假工具瞬间返回，所以一条注释就够诚实了。

**TODO 3：返回有用的错误文本。** 当 `parts.errors` 为 true 时，把真正的原因返回给模型，好让它能据此行动。为 false 时，只返回光秃秃的字符串 `"Error"`，然后看这对运行做了什么。关掉错误文本时，模型学不到 `cups_12oz` 有供应商起订量；打开时，同一个循环就有了可以据此行动的信息。重试处理的是暂时失败；有用的最终错误处理的是持续失败。

**TODO 4：写下运行日志。** 在 `runAgent` 里，`callTool` 返回之后，当 `parts.log` 开着时，把每一次调用追加到 `RUN_LOG`。没有它，「昨晚发生了什么？」这个问题根本没有答案。检查器要求日志里至少有一行。

正确的答案看起来像：无人值守的审批者默认拒绝；闸门按累计花费而不是按单笔；工具失败带着原因回来；早上能读到发生了什么。不要把完整实现从 [`SOLUTIONS.md`](../SOLUTIONS.md) 抄过来再贴回去——先让这四部分各自失败一次。
